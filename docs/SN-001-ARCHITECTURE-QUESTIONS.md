# SN-001 — архитектурные вопросы перед SN-002

Дата: 11 ноября 2026. Основание: локальный HEAD `6904096d875510ae9117012c9df53fb9b6e0bf55`,
ADR 0001–0005, восстановленная история и решения владельца из SN-001.
Связь: [roadmap](ROADMAP.md), [подтверждённый scope](adr/0006-product-scope.md).

**Все рекомендации ниже — предложения.** Они не разрешают реализацию, не меняют принятые
криптографические параметры и не заменяют ADR. SN-002 начинается только после согласования SN-001.
Рекомендуемый результат SN-002: спецификация формата, модель угроз, необходимые новые ADR и план проверок.
Q-01–Q-09 должны быть закрыты до соответствующего кода M1/M2; порядок разработки спецификации можно согласовать отдельно.

### Уточнения, которые нельзя оставить эскизом

- Q-02: исходный roadmap защищал wrap VK через `vaultId ‖ slotId ‖ formatVersion`,
  но одновременно обещал целостность всего заголовка. Нужно перечислить защищаемые поля,
  алгоритмы/параметры, правила JSON и проверки **до** дорогого KDF; простая конкатенация без кодировки недостаточна как спецификация.
- Q-03: смена пароля не отзывает старые backup/key slots и не защищает уже скопированный старый vault.
  Ротация VK, recovery, удаление slots и очистка backup требуют отдельного описания гарантий.
- Q-05: утверждение ADR 0003 про «~2³² шифрований» не является установленным безопасным бюджетом продукта.
  Следует определить допустимый риск коллизий, объём данных/число операций на ключ, ротацию и тестируемые ограничения.
  При случайном nonce это вероятностная оценка, а не абсолютная гарантия.
- Q-06: atomic rename одного файла не делает транзакцию item+blob+header атомарной.
  Нужно определить видимое состояние после каждого сбоя, поведение второго writer и restore при повреждении.
- Q-07: Ed25519 signing из спайка не доказывает совместимость с OpenSSH private-key serialization,
  а поддержка SSH не доказывает поддержку age. Возврат сохранённых байтов не должен рекламироваться как полноценная интеграция.
- Q-08: не передавать хэш clipboard-секрета через argv отсоединённого helper как автоматически безопасный контракт.
  Требуются отдельный анализ утечек, сравнение текущего содержимого и гарантии времени жизни процесса.
- Q-09: удаление записи, физическая очистка и уничтожение истории/backup — разные операции.
  Срок tombstone retention и сборку мусора нельзя определять только таймером до модели sync.

## Расхождения ADR и текущего состояния

Принятые ADR не переписываются по существу. При изменении решения создаётся новый ADR со ссылкой на заменяемый.

| Источник | Наблюдение | Действие |
|---|---|---|
| ADR 0002 | Таблицы успешных прогонов относятся к историческому спайку; библиотека ещё не в Core | Сохранить как историю; заново проверять интегрированное ядро и каждый целевой RID |
| ADR 0003 | STREAM выбран, но полного протокола нет; условие «если ADR 0002 будет принят» устарело | Не менять алгоритм в SN-001; специфицировать Q-05, отметить фактическое принятие ADR 0002 |
| ADR 0004 | «Git-синхронизация почти бесплатна» недооценивает конфликты, rollback и slots | Сохранить решение directory-per-item; стоимость и безопасность sync планировать по Q-13 |
| ADR 0005 | Указан System.CommandLine 2.0; код использует 3.0.0, Spectre ещё не подключён | Не считать UI реализованным; проверить совместимость при M3 |
| CLAUDE.md | Инструкция всё ещё указывает System.CommandLine 2.0 API | Фактическая зависимость — 3.0.0; файл инструкций не изменён автоматически, согласовать его актуализацию отдельно |
| SECURITY | Формулировка out-of-scope «until 1.0» не доказывает защиту compromised host после 1.0 | Уточнена граница обещаний; окончательную threat model согласовать в Q-01 |

## Что требуется от владельца

1. Согласовать или скорректировать предложенное разбиение M0–M4, приоритеты и версии.
2. Разрешить отдельную SN-002 как подготовку спецификации/ADR; это не разрешение на реализацию.
3. В SN-002 выбрать варианты Q-01–Q-09 и зафиксировать утверждение. Не принимать все рекомендации пакетом неявно.
4. Q-10–Q-16 закрывать перед указанными границами; серверный стек, лицензия сервера, GUI framework,
   автоматический sync, каналы пакетов и интеграции с внешними сервисами пока не утверждены.
