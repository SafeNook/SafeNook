# SafeNook vault format v1 — SN-002 draft

Status: **Proposed**, 2026-11-12; not a released or implemented format.
MUST/SHALL below define the candidate, not owner approval. Read
[threat model](threat-model.md), [recovery and I/O](recovery-and-io.md),
[storage protocol](storage-protocol.md), [decisions](SN-002-DECISIONS.md) and
[verification plan](SN-002-VERIFICATION.md) together. ADRs
[0007](adr/0007-recovery-key-slots.md), [0008](adr/0008-generation-commit.md) and
[0009](adr/0009-streaming-aead-profile.md) must be decided before implementation.
Existing accepted ADRs have not been silently replaced.

## 1. Encoding and limits

An octet is 8 bits. All binary unsigned integers are **little endian**, except the
streaming profile's explicitly big-endian chunk counter. No native struct layout,
varints, implicit padding, terminators or concatenation of variable strings is allowed.
`||` denotes byte concatenation; slices `[a:b]` exclude b. Literal magic values are
8 ASCII bytes. `D(s)` = ASCII(`SafeNook/v1/`) || ASCII(s) || byte(0); labels are exact,
case-sensitive and not user supplied. HKDF always means RFC 5869 Extract **and** Expand,
SHA-256, output 32 bytes. SHA256 and HMAC-SHA256 use complete 32-byte outputs.

IDs are 16 raw UUIDv4 bytes in RFC/network field order, not .NET Guid's mixed-endian
byte representation. On disk paths/JSON IDs use exactly 32 lowercase hexadecimal digits
without hyphens; verify version/variant bits. All-zero IDs are forbidden. A write ID is
32 independently CSPRNG-generated bytes, represented by 64 lowercase hex digits; zero
is forbidden. Never derive IDs from secret content or counters. Hex encodes byte order
as stored. Each encryption attempt gets a new write ID, even on retry/cancel/restore.

| Resource | Candidate v1 bound |
|---|---|
| `vault.json` input | 1,024 bytes; decoded header exactly 414 bytes |
| Master-password UTF-8 | 1..1,024 bytes; no normalisation or trimming |
| Item plaintext | 65,536 bytes |
| Manifest plaintext | 8,388,608 bytes |
| Blob plaintext | 26,214,400 bytes (25 MiB); zero permitted |
| Active items including tombstones | 10,000 |
| Referenced blobs | 10,000; 32 references per item maximum |
| Total active item plaintext | 268,435,456 bytes (256 MiB) |
| Total active blob plaintext | 1,073,741,824 bytes (1 GiB) |
| Retention target | Current plus one automatic previous generation; explicit backups separate |
| JSON nesting | 16 levels; no duplicate/unknown properties or nonfinite numbers |

Check physical size, fixed prefix, allowed kinds/versions, integer arithmetic overflow,
expected file length and resource totals before allocating/decrypting. Limits apply
independently to retained generations; a full rekey requires space for old and new data.
Refuse writes exceeding limits. Never truncate data to fit. No decompression exists.
Failed/interrupted GC may leave additional old roots/files; retention is not permission to
delete unverified generations. Disk exhaustion fails writes rather than sacrificing recovery.
Before unlock, all header values remain untrusted even when structurally valid.

## 2. Directory and current root

```text
vault/
  vault.json                         # sole live commit root, bounded JSON wrapper
  items/<writeId>.item                # immutable encrypted versions
  blobs/<writeId>.blob                # immutable encrypted attachments
  manifests/<writeId>.manifest        # immutable encrypted inventories
  .backup/<generationId>.json         # one retained previous root
  .tmp/<random-id>                    # ciphertext/root staging only, same filesystem
  .lock                              # persistent file; OS lock, never PID-as-lock
```

No filename comes from a record title, imported filename or unauthenticated JSON.
Root-relative paths are derived from kind and write ID, not read as paths from payloads.
The detailed physical naming and manifest addition are proposed refinements/replacements
of ADR 0004's example layout in ADR 0008; directory-per-record remains the decision.

`vault.json` is UTF-8 without BOM. It is a JSON object with exactly one string property,
`payload`, containing canonical padded RFC 4648 base64 of the binary header. No other
properties, duplicate keys, comments or trailing tokens. Whitespace/order in this wrapper
has no cryptographic meaning; whitespace INSIDE base64 is rejected. Writers emit exactly
`{"payload":"<base64>"}` followed by LF. Readers cap the wrapper at 1,024 bytes. Raw header
bytes, rather than reserialised JSON, are authenticated. This avoids canonical-JSON AAD.

## 3. Binary header, slots and authentication

Header H has prefix P (166 bytes), two slots S0/S1 (108 bytes each), then MAC (32 bytes).
Offsets below are decimal and relative to the decoded header.

| Offset | Size | Prefix field / v1 value |
|---|---|---|
| 0 | 8 | magic ASCII `SNVLT001` |
| 8 | 2 | formatVersion = 1 |
| 10 | 2 | flags = 0 |
| 12 | 16 | vaultId |
| 28 | 16 | epochId: identifies current VK epoch |
| 44 | 16 | generationId |
| 60 | 8 | sequence: 1 on init, previous+1 thereafter; overflow refuses mutation |
| 68 | 32 | parentHeaderHash: SHA256(previous decoded H), zero only at init |
| 100 | 32 | manifestWriteId |
| 132 | 32 | manifestHash: SHA256(entire manifest file) |
| 164 | 2 | slotCount = 2 |

Each slot has this fixed shape; offsets are local to its 108 bytes:

| Offset | Size | Slot field |
|---|---|---|
| 0 | 16 | slotId, distinct UUIDv4 |
| 16 | 1 | kind: 1=password, 2=recovery |
| 17 | 1 | kdf: 1=Argon2id v1.3, 0=HKDF-only recovery |
| 18 | 2 | wrapAlgorithm = 1 (AES-256-GCM) |
| 20 | 4 | mKiB |
| 24 | 4 | iterations |
| 28 | 4 | parallelism |
| 32 | 16 | salt |
| 48 | 12 | random wrap nonce |
| 60 | 32 | encrypted VK |
| 92 | 16 | GCM tag |

Slot order is password first, recovery second; no extra/duplicate slot, kind or algorithm.
Password: kdf=1, mKiB in 65,536..1,048,576 and divisible by 1,024; t=3..10; p=1.
Recovery: kdf=0, mKiB=t=p=0. Both salts are random16, regenerated with a new slot ID
and nonce on credential replacement. VK is random32; both slots wrap exactly the same VK.

```
PwdSeed = Argon2id-v1.3(passwordBytes, salt, mKiB, t, p=1, outputBytes=32)
PwdKEK  = HKDF(PwdSeed, salt=vaultId,
               info=D("password-wrap") || epochId || slotId)
RecKEK  = HKDF(RK, salt=slotSalt,
               info=D("recovery-wrap") || vaultId || epochId || slotId)
SlotAAD = D("slot") || LE16(1) || vaultId || epochId || slot[0:60]
(cipherVK, tag) = AES256GCM(KEK, slotNonce, plaintext=VK, aad=SlotAAD)
HeaderKey = HKDF(VK, salt=vaultId, info=D("header-mac") || epochId)
MAC = HMAC-SHA256(HeaderKey, D("header") || H[0:382])
```

The Argon2 variant/version, tag32, empty secret/associated-data inputs are fixed by
kdf=1. NSec memory KiB converts to libsodium bytes with checked multiplication by 1,024.
There is no password prehash, Unicode normalisation or KDF fallback.

After structural/resource checks, use only the explicitly selected slot (one attempt),
unwrap VK, verify complete header MAC with constant-time comparison, then verify manifest
hash and decrypt it. Do not publish candidate VK, names or an unlocked session earlier.
Failure wipes intermediates. Modifying parameters within limits can consume one bounded
KDF attempt but cannot produce an authenticated downgraded header without VK.

SlotAAD excludes mutable generation/manifest fields deliberately: password change can
preserve recovery slot bytes without knowing RK. Header MAC authenticates **both complete
slots, their order, every prefix field and current manifest reference**. Reject a valid
slot with invalid header MAC. An attacker can replace all of H with an authentic older H;
that is rollback, not a forgery. A damaged active slot may be bypassed only by explicit
recovery on an intact authenticated root, not by ignoring header MAC failure.

## 4. Generic encrypted envelope

Item, blob and manifest files begin with E, a 118-byte binary prefix. No trailing data.

| Offset | Size | Field |
|---|---|---|
| 0 | 8 | magic ASCII `SNOBJ001` |
| 8 | 2 | envelopeVersion=1 |
| 10 | 1 | kind: 1=item, 2=blob, 3=manifest |
| 11 | 1 | flags=0 |
| 12 | 16 | vaultId (must equal authenticated root) |
| 28 | 16 | epochId (must equal authenticated root) |
| 44 | 16 | objectId: stable logical item/blob ID; generationId for manifest |
| 60 | 32 | writeId (must equal derived path and manifest/header reference) |
| 92 | 2 | type: 1=login, 2=note, 3=SSH, 4=age, 5=file; zero for blob/manifest |
| 94 | 2 | schema=1 |
| 96 | 2 | algorithm: 1=whole AES-256-GCM; 2=stream profile below |
| 98 | 8 | plaintext length L |
| 106 | 12 | random nonce for algorithm1; all zeros for algorithm2 |

```
ObjectKey = HKDF(VK, salt=vaultId, info=D("object-key") || E[0:106])
ObjectAAD = D("object") || E
```

Items/manifests require algorithm1. Their suffix is ciphertext[L] || tag[16]; exact file
length 118+L+16. GCM uses ObjectKey, E.nonce and ObjectAAD. Whole plaintext authenticates
before JSON parsing or output. The immutable context commits vault, epoch, logical ID,
write ID, type, schema, algorithm and length. A type change cannot be interpreted under
a different schema by relabelling bytes. Record type is observable ciphertext metadata.

New write ID + new nonce for every encryption attempt; immutable files are never edited
in place or re-encrypted with the same E. Retrying installation may copy **identical already
encrypted bytes**, but never encrypt new bytes under that identity. With <=2^32 attempted
writes per VK epoch, random256 write-ID collision probability is approximately <=2^-193;
this probabilistic bound assumes an uncompromised CSPRNG and independent draws. The policy
requires a fresh VK epoch before exceeding that operational budget. It is not a trusted
anti-rollback counter. Restored/copied writers must draw fresh randomness, not restore RNG
state. Domain-separated per-write keys avoid a long-lived random96-nonce GCM key.

## 5. Blob streaming profile (M2; proposed ADR 0009)

Use the **RAW AES-GCM-HKDF Streaming encryption function** specified by
[Tink](https://developers.google.com/tink/streaming-aead/aes_gcm_hkdf_streaming), not an
invented sequence of independent AEAD messages. Parameters: KeyValue=ObjectKey,
DerivedKeySize=32, HkdfHashType=SHA256, CiphertextSegmentSize=65,536,
AssociatedData=ObjectAAD; firstSegmentOffset=0, no Tink keyset/output prefix.
The 118-byte SafeNook prefix is outside that stream. Blobs require kind2/type0/schema1,
algorithm2 and zero envelope nonce.

Profile summary for independent parsing (the linked function defines encryption):
stream header = byte(40) || randomSalt32 || randomPrefix7. Segment key is HKDF(KeyValue,
salt=randomSalt32, info=ObjectAAD). Chunk nonce = prefix7 || BE32(index) || finalByte;
index starts at zero, finalByte is 1 only on the last segment, otherwise 0. Each segment
uses AES-256-GCM, empty per-segment AAD and tag16. First plaintext segment capacity is
65,480 bytes, later capacity 65,520; every non-last segment is full. Empty input has one
empty final segment. No extra empty segment follows an exactly full last segment.

For L<=25 MiB, n=1 when L<=65,480, otherwise
n=1+ceil((L-65,480)/65,520). Thus 1<=n<=401. The whole file has exactly
118+40+L+16*n bytes, maximum 26,220,974 bytes. The final flag is encoded into the nonce,
not stored as an unauthenticated flag in the stream. Readers derive expected n and
segment lengths from bounded E.L, enforce final authentication and exact EOF. Check
manifest ciphertext hash, all segment tags and total length before providing final
plaintext; never treat tag failure as EOF. Reordering, duplication, truncation and
cross-write chunk substitution must fail. Replaying a complete historical blob is
rejected by the current manifest, but replaying a complete old root remains possible.

This changes ADR 0003's blanket random96 nonce rule for chunks and clarifies that 64 KiB
is a **ciphertext segment** size. Adoption requires ADR 0009, cross-implementation vectors
and review. Using this description does not make a new .NET implementation audited.
Prefer an existing reviewed implementation of this function if AOT-compatible; otherwise
block M2 release pending reviewed port. No library/dependency is selected in SN-002.
Alternatives and their approval consequences are recorded in ADR 0009.

Whole-file release: because blobs are capped, decrypt into a private bounded memory
buffer, check every segment, then export. Do not decrypt a second mutable read after
verification; use the same verified plaintext. No partial stdout or plaintext disk spool.
Memory shortage fails without changing the vault or destination.

## 6. JSON plaintext rules

Items and manifests are strict UTF-8 JSON without BOM or invalid Unicode/surrogates.
Reject duplicate properties at every level, unknown properties, unknown enum values,
comments, trailing commas/tokens and depth>16. Numbers representing unsigned integers
use integer decimal tokens (no sign, fraction or exponent), fit UInt64, and are range
checked; writers use minimal decimal. Property order/whitespace has no semantic meaning:
AEAD authenticates original bytes and ciphertext hashes do not depend on reserialisation.
Do not regenerate ciphertext just to reformat JSON. String lengths below are UTF-8 byte
counts after JSON decoding. Dates are UTC Unix milliseconds, integer 0..253402300799999;
updatedAt>=createdAt per record, but clocks confer no ordering authority across devices.

All fields described below are required unless explicitly nullable. `null` differs from
missing. No polymorphic reflection, type-name-based dispatch or unknown-type fallback.
Use explicit DTOs, source-generated System.Text.Json contexts, bounded Utf8JsonReader
prevalidation (including duplicates) and checked arithmetic under Native AOT. The future
implementation must prove these constraints; source generation alone does not enforce them.

### Manifest

Properties: `schema`=1, `vaultId`, `epochId`, `generationId`, `sequence`,
`parentHeaderHash` (hex64), `items` array, `blobs` array. Header fields must match exactly.
Each array contains references with exactly `id` (hex32), `writeId` (hex64), `type`
(integer, item1..5 or blob0), `length` (plaintext bytes), `sha256` (hex64 of entire file).
Arrays are sorted by raw ID bytes ascending, without duplicates. All write IDs are unique
across the manifest. Manifest size and aggregate limits from section 1 apply.

Manifest objectId is current generationId; header supplies its writeId/hash. At normal
unlock authenticate root, manifest, **all current items** and their schemas; only then
construct session metadata. Blobs are lazy: verify existence/type/size without allocating
them on unlock, authenticate full bytes before extraction/use. Backup verification checks
all blobs. A missing file referenced by the current manifest is corruption, never an empty
record. Extra files are unreachable candidates, never auto-imported or used to fill holes.
Every blob reference in an item must match one manifest blob; every manifest blob must be
referenced by exactly one live item. Shared ownership/deduplication is not supported in v1.

### Item common fields

Properties: `schema`=1, `id`, `type` (same integer as E), `revision` (1..UInt64.MaxValue),
`createdAt`, `updatedAt`, `title` (0..1,024 bytes), `tags` (<=32 distinct strings each
1..64 bytes), `deleted` (boolean), `previous` (null or hex64 SHA256 of previous entire
item file), `payload` (type-specific object, or null for tombstone).
`id`, type, schema and physical L agree with envelope/manifest. Revision increments for
an item edit; refuse overflow. `previous` is null for creation, otherwise a hash identity,
not a promise that historical bytes remain locally. `type` cannot change on a logical ID.
A replacement type gets a fresh ID and tombstones the old item. Timestamps/title/tags are
inside encryption, never filenames. No extension-property bag in schema1.

A tombstone has deleted=true, payload=null, title empty and tags empty; other common fields
remain meaningful. It has no blob references. Tombstones persist until an explicit reviewed
purge; no time-based GC. History is not a list of plaintext revisions: previous hashes and
retained generation permit only limited recovery in M1/M2. Full user-facing history is M3.
No automatic conflict winner is chosen from revision, generation sequence or timestamps.

### Payloads and M2 byte preservation

| Type | Required payload fields / limits |
|---|---|
| 1 login | `username` string<=4,096; `password` string<=4,096; `urls` array<=16 strings each<=2,048; `notes` string<=32,768 |
| 2 note | `text` string<=32,768 |
| 3 SSH | `privateBlobId` hex32; `publicBlobId` null or hex32; `format`=`opaque-ssh`; `originalName` string<=255 |
| 4 age | `identityBlobId` hex32; `recipientBlobId` null or hex32; `format`=`opaque-age`; `originalName` string<=255 |
| 5 file | `blobId` hex32; `originalName` string<=255; `mediaType` string<=255 |

An entire item must also meet its 65,536-byte encoded limit. Login/note have no attachments
in schema1. Every referenced blob ID belongs to the same vault/epoch inventory and one item.
Imported SSH/age inputs (each <=1 MiB) and public/recipient companions (each <=64 KiB) are
stored as opaque bytes: preserve BOM, comments, line endings, trailing newline and encrypted
key bytes exactly. Allow native age identity text, plugin identity text, OpenSSH/PEM and
unknown variants only as explicitly labelled **unvalidated storage**, never as proven usable
keys. No decryption, key-format validation, execution, agent loading or plugin invocation.
User confirmation labels unvalidated imports; do not claim a public companion matches its
private key. No SSH-key generation or age engine is required in M2. General file blobs have
the 25 MiB limit. Original names are display hints, not export paths; sanitize display and
require a separately chosen destination. Do not deduplicate by plaintext hash.

## 7. Versions, failure and independence

Unknown header/envelope/schema version, flag, kind, algorithm or item type is
UnsupportedFormat: fail closed, leave files untouched and recommend a compatible client.
Malformed/truncated/oversized data is InvalidFormat or ResourceLimit before crypto where
possible. Authentication failure is AuthenticationFailed; missing/inconsistent inventory
is CorruptGeneration. Errors carry safe categories and object IDs, never secret input or
raw JSON. Do not automatically repair by skipping bad records. Explicit salvage is read-only
and reports omissions; it is not successful complete unlock/restore.

No format upgrade by write-on-read. Future migration requires a separately approved
version, backup and atomic publication; legacy PasswordGeneratorCLI import remains excluded.
These layouts plus [verification fixtures](SN-002-VERIFICATION.md) are sufficient to write
an independent structural parser; cryptographic vectors and implementation remain future
work. HKDF definition and vectors: [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.txt).
