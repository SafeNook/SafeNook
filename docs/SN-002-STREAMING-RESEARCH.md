# SN-002-R1 — выбор шифрования вложений SafeNook

Дата: 12 ноября 2026. Статус: **исследование и рекомендация для обсуждения**, не утверждение ADR и не реализация vault. Основание: лимит файла 25 МиБ, полная аутентификация до выдачи plaintext, .NET 10 / Native AOT и immutable objects с authenticated manifest/COW. Связанные документы: [формат](vault-format.md), [ADR 0003](adr/0003-aead-cipher.md), [Proposed ADR 0009](adr/0009-streaming-aead-profile.md), [модель угроз](threat-model.md), [план проверок](SN-002-VERIFICATION.md).

**Для текущих требований рекомендуется whole-object AES-256-GCM через .NET BCL.** Он обходится без нового криптографического пакета или native interop, а измеренные затраты для 25 МиБ — около 50 МиБ дополнительных payload-буферов и 27–28 мс на полную файловую операцию на проверенной Windows x64 машине. Это вывод о практичности и поверхности сопровождения, а не доказательство превосходства AES над XChaCha20 или безопасности всего SafeNook. Secretstream — работоспособная альтернатива с меньшим потреблением памяти, если это преимущество станет необходимым требованием; сегодня она добавляет собственный ABI-адаптер и новый framing. Официальная .NET-реализация Tink не установлена; проверенный сторонний порт работает под AOT, но не соответствует профилю 64 КиБ и содержит нежелательное обращение с plaintext-буферами. Выбор BCL потребует явного изменения решения STREAM в ADR 0003 через ADR 0009; **статусы и содержимое этих ADR в SN-002-R1 не менялись**.

### Tink: опубликованный профиль подходит, доступный .NET-порт — другой продукт

Параметры ADR 0009 соответствуют формальному RAW AES-GCM-HKDF Streaming: key32, SHA256, header40, firstSegmentOffset=0, ciphertext segment65,536. Отсюда первый plaintext segment65,480, следующие65,520; для 25 МиБ — 401 сегмент и 26,220,974 байта вместе с внешним prefix118. Это сверка параметров и арифметики, **не проверка ciphertext межъязыковыми vectors**. Официальный Java constructor допускает эти параметры. ([Формальный профиль](https://developers.google.com/tink/streaming-aead/aes_gcm_hkdf_streaming), [Java implementation](https://github.com/tink-crypto/tink-java/blob/v1.24.0/src/main/java/com/google/crypto/tink/subtle/AesGcmHkdfStreaming.java))

Проверенный `TinkStreamingAead` фиксирует ciphertext segment1,048,576; публичной настройки 64 КиБ нет. Он избавляет SafeNook от написания собственного порта только ценой доверия стороннему порту, написанному самостоятельно. Его SECURITY.md сообщает об отсутствии независимого аудита и поддержке исправлений в новейшей версии, без обещания долгосрочной поддержки старых версий. Ограниченная история сопровождения не доказывает заброшенность, но не даёт оснований объявить пакет равноценным официальной реализации Google. ([Pinned implementation](https://github.com/salehalakhras/TinkStreamingAead/blob/93c37582d8f436517c67fa44253c7c45e2215e8d/src/TinkStreamingAead/Aes256GcmHkdf1MB.cs#L28), [Security policy](https://github.com/salehalakhras/TinkStreamingAead/blob/93c37582d8f436517c67fa44253c7c45e2215e8d/SECURITY.md))

Обнаружены конкретные издержки интеграции: encrypt/decrypt возвращают внутренние plaintext-массивы в `ArrayPool.Shared` без очистки; decrypt записывает отдельные проверенные сегменты в caller stream до проверки конца файла. Последнее является нормальной streaming-семантикой, но требует приватного полного буфера для политики SafeNook. Внешний буфер решает раннюю выдачу, но **не очищает уже возвращённые внутренние массивы**. PoC не исправлял пакет, поэтому измерения относятся к исходной версии. Это наблюдение кода, а не утверждение об извлечении секретов из памяти действующего vault. ([Encrypt cleanup](https://github.com/salehalakhras/TinkStreamingAead/blob/93c37582d8f436517c67fa44253c7c45e2215e8d/src/TinkStreamingAead/Aes256GcmHkdf1MB.cs#L226), [early output and cleanup](https://github.com/salehalakhras/TinkStreamingAead/blob/93c37582d8f436517c67fa44253c7c45e2215e8d/src/TinkStreamingAead/Aes256GcmHkdf1MB.cs#L296))

Путь через официальный C++ Tink и собственный C ABI adapter не требует переписывать конструкцию, но добавляет отдельную native поставку, toolchain и ABI; его практичность здесь не доказана. Для оставленного Tink-профиля понадобятся pinned официальный oracle, оба направления interop, одинаковые RAW/key/AAD/segment parameters, empty/full-boundary и negative vectors. Нынешний порт 1 МиБ не проверяет ADR-профиль 64 КиБ без изменения исходников. Стоимость межъязыковых тестов — отдельный поддерживаемый harness/toolchain и fixtures при каждом обновлении; трудозатраты в днях не измерялись.

### Secretstream: готовая конструкция, но новый interop и файловый framing

В проверенном NSec имеются только упоминания secretstream в interop-описании, а не публичный wrapper. Без собственного порта конструкции можно вызвать официальный libsodium C API через `LibraryImport`: `size_t` отображается в `nuint`, длины `unsigned long long` — в `ulong`, tag — в byte, calling convention — Cdecl. Следует запрашивать ABI-размеры, владеть состоянием с гарантированным освобождением/очисткой и проверять return codes, границы и время жизни pointers. Это дополнительный код сопровождения, даже если алгоритм остаётся внутри libsodium. ([NSec source](https://github.com/ektrah/nsec/tree/02c51bb20a7b6accc96e74ecab6e2659cc1f5c63/src), [libsodium header](https://raw.githubusercontent.com/jedisct1/libsodium/1.0.22-RELEASE/src/libsodium/include/sodium/crypto_secretstream_xchacha20poly1305.h))

В PoC использованы key32, header24, overhead17 на сообщение, state52 и обязательный `FINAL` на последнем сообщении с точным EOF. Официальная API управляет stream state/nonce/rekey; приложение всё равно должно задать framing и отказ от неполного файла. Статический `.lib` libsodium1.0.22 успешно слинкован через `DirectPInvoke`/`NativeLibrary`, exe работает без DLL рядом. Это доказывает **win-x64**, не новые symbols/ABI на всех семи RID старого NSec-спайка. Windows ARM64, Linux glibc/musl и macOS требуют отдельных прогонов. ([Official secretstream API](https://doc.libsodium.org/secret-key_cryptography/secretstream), [Native AOT interop](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/interop))

### BCL: явное владение буферами и один authentication boundary

`AesGcm` принимает caller-owned spans, nonce12, tag16 и AAD. Для .NET 8+ ошибка tag вызывает `AuthenticationTagMismatchException`; API документирует очистку plaintext при провале tag. SafeNook всё равно должен удерживать результат до успешного возврата и очищать собственные буферы в `finally` при любом исключении. `Span` устраняет лишние копии, но не превращает one-shot API в streaming; PoC использует отдельные plaintext/ciphertext arrays и не предполагает безопасное in-place overlap. Поддержку проверяет `AesGcm.IsSupported`. ([Encrypt](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.aesgcm.encrypt?view=net-10.0), [Decrypt](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.aesgcm.decrypt?view=net-10.0))

Windows, Linux и Apple используют разные платформенные пути BCL; отсутствие нового native пакета SafeNook не означает отсутствие зависимости от ОС. Локальный AOT-run не заменяет кроссплатформенную проверку и не устанавливает FIPS compliance. ([Windows source](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/Common/src/System/Security/Cryptography/AesGcm.Windows.cs), [OpenSSL source](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/System.Security.Cryptography/src/System/Security/Cryptography/AesGcm.OpenSsl.cs), [Apple source](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/System.Security.Cryptography/src/System/Security/Cryptography/AesGcm.Apple.cs))

## 2. Все три PoC работают под AOT, но проверяют разный объём контракта

Проекты находятся только в `spikes/AttachmentCryptoResearch`, не добавлены в `SafeNook.slnx`, не ссылаются на Core и не меняют production-зависимости или CI. Тестовые ключи и данные синтетические. Общая фактически проверенная платформа: Windows 11 build26300, x64, Intel Core i7-12650H, доступная системе RAM около65,237 МиБ, SDK10.0.404; BCL executable сообщает runtime10.0.15. Сведения среды и методика сохранены рядом с raw results. ([BCL environment](../spikes/AttachmentCryptoResearch/Bcl/results/environment.json), [Tink environment](../spikes/AttachmentCryptoResearch/Tink/results/environment.json))

| PoC | Фактически выполнено | Проверка недопустимого ввода | Что не доказано |
|---|---|---|---|
| [BCL](../spikes/AttachmentCryptoResearch/Bcl/README.md) | AOT win-x64 без предупреждений; **40 checks**; размеры0/1/5/10/25 МиБ | Ciphertext/tag/AAD/context/length mutation, truncation, append; destination не создаётся при authentication failure | Независимая реализация полного envelope/manifest и файловая crash consistency |
| [SecretStream](../spikes/AttachmentCryptoResearch/SecretStream/README.md) | Static AOT win-x64 без предупреждений; **76 checks**; те же размеры плюс1byte/64КиБ boundaries | Header/ciphertext/tag/AAD/length mutation, truncation/append, перестановка двух chunks; destination отсутствует | Независимые KAT/transcripts, production framing и другие RID |
| [Tink-порт](../spikes/AttachmentCryptoResearch/Tink/README.md) | AOT win-x64 без предупреждений; **88 checks**; те же размеры плюс1byte/1МиБ-profile boundaries | Ciphertext/tag/AAD mutation, truncation/append/header-only; внешний published stream остаётся пустым | Официальный межъязыковой interop, профиль64КиБ и безопасность внутреннего pool lifecycle |

Пустой файл проверен во всех трёх вариантах. Количество checks отражает разные harness и границы, а не относительную криптографическую надёжность. BCL дополнительно прошёл один публичный AES-256-GCM known-answer case из [BoringSSL collection](https://boringssl.googlesource.com/boringssl/+/1d134eee9a7f456cc100ac450abcc67243d8fbdd/crypto/cipher/test/aes_256_gcm_fips_testonly_tests.txt); это не полный NIST CAVP прогон. SecretStream/Tink прошли round-trip и negative tests, но независимые interop/KAT для них **не выполнялись**; утверждения upstream о vectors не засчитываются как проверки SafeNook. [Upstream secretstream tests](https://raw.githubusercontent.com/jedisct1/libsodium/1.0.22-RELEASE/test/default/secretstream_xchacha20poly1305.c) — будущий источник regression fixtures, не независимое доказательство нашего framing.

BCL PoC использует экспериментальный prefix118, HKDF-SHA256 per-write separation, новые writeId32/nonce12 и внешний ожидаемый контекст. Комбинация blob kind2/algorithm1 сейчас запрещена draft `vault-format.md`: PoC изучает предлагаемую альтернативу, а не уже совместимый формат. SecretStream использует исследовательский `LE64(length)||header24||chunks` с AAD из domain/total length/index/chunk length; Tink — фиксированный RAW1МиБ и синтетический AAD. У двух streaming PoC нет полной SafeNook118-byte оболочки/HKDF/manifest. Поэтому сравниваются конкретные адаптеры, а не три взаимозаменяемых production codecs. ([BCL source](../spikes/AttachmentCryptoResearch/Bcl/Program.cs), [SecretStream source](../spikes/AttachmentCryptoResearch/SecretStream/Program.cs), [Tink source](../spikes/AttachmentCryptoResearch/Tink/Program.cs))

Immutable/COW совместимость установлена на уровне контракта: новый ciphertext-файл, его полный hash в authenticated inventory, новая identity на каждое шифрование и публикация после проверки. Для BCL дополнительно проверено равенство SHA256 побайтовой COW-копии ciphertext. Полноценного store/manifest transaction ещё нет: atomic replacement, ACL, lock, symlink attacks, disk-full, crash/power-loss и root publication **не тестировались**. Research framing не становится утверждённым криптографическим протоколом от успешного round-trip.

## 3. Измерения показывают цену буферов, а не универсального победителя

Выполнено **150 операций в свежих AOT-процессах**: три варианта × пять размеров × encrypt/decrypt × пять повторов. Варианты запускались последовательно, без одновременных build/benchmark других исследователей; обычная фоновая нагрузка ОС не контролировалась. Перед каждой измеряемой операцией выполнен warmup64КиБ, GC и baseline. Fixtures подготовлены заранее; filesystem cache не очищался. Полное время включает allocation, read/write, crypto, обычный Flush/dispose и очистку собственных буферов; **не включает durable flush/COW commit**. BCL включает свой HKDF/envelope, streaming harness имеют другую обвязку. Поэтому числа не изолируют стоимость одного шифра и не предсказывают Linux/macOS/ARM.

### Расчёт BCL памяти совпал с наблюдаемым порядком роста

| Plaintext, МиБ | Exact arrays: plaintext + ciphertext, МиБ | Два pooled buffers по .NET10 bucket arithmetic, МиБ |
|---:|---:|---:|
| 1 | 2 | 2 |
| 5 | 10 | 16 |
| 10 | 20 | 32 |
| 25 | 50 | 64 |

Левая колонка — расчёт одновременных payload arrays конкретного PoC, подтверждённый allocation примерно2N+6КиБ. Он читает прямо в plaintext/ciphertext array и пишет его span без третьего N-sized output; FileStream bufferSize1 отключает дополнительную managed буферизацию. Prefix118/tag16/keys, provider, runtime, GC и ОС добавляют расходы поверх2N. Наивные `ReadAllBytes` + `MemoryStream.ToArray` могут создавать дополнительные N-sized копии; streaming source/output не требует отдельного полного массива вывода. ([PoC implementation](../spikes/AttachmentCryptoResearch/Bcl/Program.cs))

Правая колонка — **не измерение**, а расчёт bucket sizes по опубликованной .NET10 реализации: запросы5/10/25МиБ округляются до8/16/32МиБ на массив. Pooling может уменьшить повторные allocation в длинной сессии, но удерживает память и усложняет владение. Чувствительный rented buffer следует явно очистить целиком через `CryptographicOperations.ZeroMemory` до `Return`; нельзя полагаться только на `clearArray:true`, поскольку contract связывает очистку с удержанием массива пулом. После возврата использовать массив запрещено. `Span` помогает избежать копий, но не очищает память автоматически. Для первой реализации рекомендуется exact arrays с явным lifetime; pooled вариант отдельно измерять под реальной сессионной нагрузкой. ([Bucket source](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Buffers/Utilities.cs), [ArrayPool.Return contract](https://learn.microsoft.com/en-us/dotnet/api/system.buffers.arraypool-1.return?view=net-10.0))

Secretstream encryption удерживает примерно два64КиБ chunk buffers, decrypt — N-byte private plaintext плюс ciphertext chunk. Tink-порт также удерживает полный private plaintext при decrypt плюс внутренние сегменты/pools. Поэтому **потоковое шифрование экономит второй полный массив, но не даёт O(1) RAM для расшифрования при действующей политике выдачи**. Для больших файлов нужны не только новый лимит и stream primitive, но и отдельное решение о проверенном immutable ciphertext snapshot/quarantine. Двухпроходное чтение изменяемого файла небезопасно считать готовым решением: изменение между проверкой и выдачей может проявиться после раскрытия части данных. Параллельные операции, уже расшифрованные metadata vault и запас под OOM в этих isolated measurements не моделировались.

## 4. Сравнение по десяти критериям отдаёт приоритет простоте текущего scope

| Критерий | Tink AES-GCM-HKDF Streaming | libsodium secretstream | Whole-object BCL AES-GCM |
|---|---|---|---|
| 1. Криптографическая обоснованность | Опубликованная конструкция и анализ; безопасность конкретного .NET-порта отдельно | Готовая stateful конструкция libsodium; framing/FINAL policy отдельно | Стандартный AEAD; границы nonce/key/AAD/framing всё равно требуют review |
| 2. Проверенная реализация | Официальная есть в других языках; проверенный .NET-порт прямо unaudited | Официальная native библиотека; собственный небольшой ABI wrapper | Штатная платформа .NET/OS, без нового crypto пакета |
| 3. .NET и Native AOT | Сторонний1МиБ порт прошёл win-x64; официальный64КиБ .NET путь не установлен | Direct P/Invoke static win-x64 прошёл; остальные RID впереди | BCL AOT win-x64 прошёл; API поддерживает целевые ОС, их прогоны впереди |
| 4. Сопровождение | Port/fork или C++ bridge, review, межъязыковой oracle, pool cleanup | ABI/version/state ownership, framing и совместная native поставка | Меньше собственного interop/протокольного кода; обновления .NET/ОС |
| 5. Память | Encryption bounded; decrypt N+segment/pool при полной проверке | Encryption bounded; decrypt N+chunk | Простой вариант2N; около50МиБ payload arrays для25МиБ |
| 6. Производительность | Измерен только сторонний1МиБ порт; самый быстрый encrypt в этом harness | Оба направления уложились в~40–47мс для25МиБ | Оба направления~27–28мс; требования не заставляют усложнять реализацию |
| 7. Кроссплатформенная поставка | Official native bridge увеличит зависимости; managed-port support не доказан на всех ОС | Можно использовать существующую libsodium supply chain, но новый ABI тестируется отдельно | Нет дополнительной native библиотеки в поставке SafeNook; OS providers остаются |
| 8. Большие файлы | Конструкция подходит, release policy требует пересмотра | Конструкция/rekey подходят, release policy требует пересмотра | O(N) буферы ограничивают рост; будущий format migration нужен при реальной потребности |
| 9. ADR 0002–0004 | Сохраняет AES/STREAM идею, но .NET1МиБ не соответствует выбранному профилю | Сохраняет libsodium/directory, требует разрешить XChaCha для blobs вместо ADR0003 | Сохраняет AES/libsodium для прежних задач/directory, требует явно заменить STREAM-clause ADR0003 |
| 10. Независимое тестирование | Два языка, pinned exact RAW profile, vectors и review порта | Отдельный C adapter/transcripts, ABI и framing negative tests | Primitive KAT и независимые envelope/HKDF vectors, меньше stream boundary states |

Не выявлено требования, для которого экономия примерно22МиБ working set на расшифровании25МиБ сама по себе оправдывает новый native wrapper или сторонний криптографический порт. Это инженерная оценка на проверенной машине, а не универсальный memory budget для любого устройства. Если владелец задаст более строгий бюджет RAM, secretstream следует рассматривать первым потоковым резервным вариантом: native библиотека уже принята, а конструкцию не придётся портировать. Tink имеет смысл возвращать в shortlist при наличии проверенного сопровождаемого .NET пути или при осознанном принятии bridge/port/interop затрат, а не только из-за возможного роста файлов.

## 5. Предлагаемое изменение ADR требует решения владельца и новых vectors

Следующая таблица — **предложение**, не применённый patch. Действующий Proposed ADR 0009 не считается окончательным решением; принятый ADR 0003 не переписывается по существу без процедуры замены.

| Документ | Предлагаемое изменение после согласования |
|---|---|
| ADR 0009 | Переформулировать решение как whole-object BCL AES-256-GCM для blobs<=25МиБ; зафиксировать явную замену STREAM-части ADR0003, стоимость2N и условия повторного рассмотрения streaming; сохранить альтернативы |
| ADR 0003 | После принятия нового ADR добавить статус/ссылку о замене только attachment streaming решения; AES256GCM для остальных назначений сохраняется |
| `vault-format.md` | Для blob kind2 разрешить algorithm1, nonce12 random, ciphertext[L]+tag16, точный размер118+L+16; максимум26,214,534 байта, пустой объект134 байта; убрать требование нулевого envelope nonce для этого алгоритма |
| `vault-format.md` и crypto vectors | Сохранить per-write HKDF `D("object-key")||E[0:106]`, AAD `D("object")||E`, fresh writeId32 и nonce12 на каждое шифрование/повтор, expected vault/epoch/object/type/schema/length и полный manifest hash; ни fallback, ни переинтерпретации неизвестного algorithm |
| `threat-model.md` / I/O | Для T05 описать whole-object boundary: точная длина/EOF плюс единая tag-проверка до output; включить2N budget/OOM и zeroisation limits; не ослаблять запрет раннего plaintext |
| `SN-002-VERIFICATION.md` | Заменить обязательные v1 chunk fixtures на whole-object boundary/empty/max+1/tamper/AAD/EOF/length tests; оставить STREAM interoperability отдельным gate будущего формата; добавить independent full-envelope vectors и provider matrix |
| COW/storage | Сохранить immutable file/write identity, ciphertext hash и atomic root publication; перед commit верифицировать новый объект; существование этих правил не означает, что PoC испытал crash consistency |

До allocation требуется проверить fixed header, допустимые version/kind/algorithm, длину<=25МиБ и точный размер файла. Использование свежего per-write key не отменяет nonce discipline: повтор шифрования получает новые write ID и nonce; побайтовое копирование уже зашифрованного объекта для COW/backup не является новым encryption. При неверном tag/AAD/контексте результат не публикуется, собственные ключевые и plaintext-буферы очищаются. Отдельно нужны обработка OOM/отмены, безопасные права и атомарная публикация, которых research harness намеренно не реализует.

При будущем переходе на streaming потребуется новый явно специфицированный authenticated algorithm/profile или версия формата, новые bounds/vectors и отказ старого reader на неизвестном значении. Миграция — decrypt/verify старого объекта, encrypt в новую immutable identity, проверка полного результата и переключение manifest/root через COW с сохранением проверенного backup. Нельзя менять значение уже выпущенного algorithm1, незаметно подменять размер сегментов или читать новый формат как старый. Для secretstream дополнительно нужны новое cipher identifier, header24/overhead17, framing/FINAL/EOF/AAD и новые ABI-тесты; для Tink — точный reviewed профиль и рабочий официальный-language oracle.

Владельцу предлагается утвердить BCL whole-object для текущего лимита, принять его измеренную цену памяти как кандидат budget и разрешить отдельное изменение Proposed ADR 0009 с явной связью с ADR 0003. Перед production-интеграцией остаются independent HKDF/envelope vectors, более полный primitive KAT corpus, Windows/Linux/macOS AOT/provider matrix, memory-pressure/cancellation tests и review framing/key lifecycle. Для streaming альтернатив дополнительно обязательны независимые transcripts/interop и review interop/порта. **Ни успешный AOT, ни204 локальных checks, ни150 измерений не доказывают безопасность готового vault**; они позволяют выбрать более обоснованную конструкцию до её реализации.
