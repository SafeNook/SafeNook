# 0009. Whole-object AES-256-GCM для вложений до 25 МиБ

- **Статус:** Предложено (Proposed), редакция SN-002-R2 ожидает согласования.
- **Дата:** 2026-11-12
- **Основание выбора:** владелец подтвердил whole-object BCL AES-256-GCM в SN-002-R2.
- **Частичная замена:** attachment STREAM-часть ADR 0003; AES-GCM для остальных объектов
  и nonce/tag остаются. Формальное принятие этой редакции — отдельный следующий шаг.
- Историческое имя файла сохранено для стабильности ссылок.

## Контекст и история

ADR 0003 выбрал STREAM/GCM с чанками 64 КиБ. Первая редакция ADR 0009 предлагала
Tink RAW AES-GCM-HKDF Streaming, но не была принята. [Исследование R1](../SN-002-STREAMING-RESEARCH.md)
сравнило BCL, secretstream и сторонний Tink-порт на изолированных AOT PoC.
Полная аутентификация до выдачи plaintext и лимит 25 МиБ позволяют обойтись одним AEAD
вызовом без нового streaming-протокола. История исследования сохранена без правок.

## Новая редакция решения

Для blob v1 использовать System.Security.Cryptography.AesGcm из .NET BCL:
AES-256-GCM, algorithm=1, случайный nonce 12 байт, tag 16 байт.
Файл: envelope[118] || ciphertext[L] || tag[16], 0 <= L <= 26 214 400.
Максимальный файл — 26 214 534 байта, пустой — 134 байта.

Сохранить per-write HKDF, новый writeId32 и nonce12 при каждом шифровании/повторе,
ObjectAAD = D("object") || E и проверки vault/epoch/object/type/schema/length.
Идентичное копирование уже зашифрованного immutable объекта — не новое шифрование.
Полные байтовые контракты заданы в [формате](../vault-format.md).

До выделения буферов проверить размеры, контекст, поддерживаемый algorithm и точный EOF.
После Decrypt проверить успех аутентификации до любой публикации plaintext. При любой
ошибке/отмене очистить собственные ключевые и plaintext-буферы; не полагаться только на
очистку внутри API. Использовать отдельные массивы и Span без лишних полноразмерных копий.
ArrayPool не требуется для первой реализации. In-place overlap не предполагается.

Рабочая модель памяти — около 2L payload bytes плюс runtime/provider/metadata overhead;
для 25 МиБ это 50 МиБ массивов. R1 измерил около 61 МиБ process working set на Windows x64,
но это не универсальный бюджет и не гарантия под memory pressure. OOM/отмена не изменяют
текущий root и не публикуют частичный результат. Параллельные операции требуют admission
budget. Нельзя незаметно уменьшить лимит файла или переключить алгоритм при нехватке RAM.

## Альтернативы и причины отказа от streaming в v1

| Вариант | Оценка для текущих требований |
|---|---|
| Whole-object BCL AES-GCM | Выбран владельцем: минимум новых компонентов, единая authentication boundary; цена — 2L памяти |
| Tink AES-GCM-HKDF Streaming | Опубликованная конструкция, но официальная .NET реализация не установлена; проверенный порт фиксирует 1 МиБ, unaudited и не очищает внутренний plaintext pool |
| libsodium secretstream | Работоспособный резерв, но нужен отдельный interop/framing и новый выбор AEAD для blobs; decrypt всё равно удерживает полный plaintext при текущей политике |
| Собственный порт/склейка chunks | Не допускается без отдельного review; будущие большие файлы сами по себе не оправдывают эту сложность сейчас |

Streaming не является обязательным профилем v1; algorithm=2 в v1 не поддерживается.
При реальной потребности в больших файлах нужен новый согласованный algorithm/profile
или format version, independent vectors и новая политика памяти/выдачи. Старый reader
должен отказать на неизвестном алгоритме, а не угадать формат. Миграция использует новые
immutable identities, проверку результата и COW commit с backup.

## Последствия и согласование

ADR 0002 (Argon2id/Ed25519 через NSec) и каталог из ADR 0004 сохраняются; COW/manifest
уже приняты в ADR 0008. Это не ослабляет полную аутентификацию до export/reveal.
Нужны independent HKDF/envelope vectors, negative tests, Windows/Linux/macOS AOT/provider
checks, memory-pressure/cancellation и review. R1 не испытывал production store.

Владелец уже выбрал алгоритм и лимит; требуется согласовать именно эту редакцию ADR 0009,
после чего отдельно перевести её в Accepted. Прикладной код и SN-003 не разрешаются этим
документом автоматически.
