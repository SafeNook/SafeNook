# 0003. AES-256-GCM как AEAD

- **Статус:** Принято
- **Дата:** 2026-10-21

## Уточнение SN-002-R2 (2026-11-12)

Выбор AES-256-GCM сохранён. Владелец заменил STREAM для вложений до 25 МиБ на
whole-object AES-256-GCM через BCL. [Новая редакция ADR 0009](0009-streaming-aead-profile.md)
фиксирует эту **частичную замену** и пока ожидает согласования текста (Proposed).
Обязательные контракты v1 в [формате](../vault-format.md) уже приведены к решению владельца:
nonce12, tag16, per-write HKDF, полная аутентификация до выдачи plaintext.
Нижеследующий текст сохранён как историческая редакция; его STREAM/chunk-правило не является
требованием v1 после SN-002-R2. Остальные назначения AES-GCM этим не отменяются.

## Контекст

Предыдущая утилита использовала AES-CBC без аутентификации: подмена шифртекста не обнаруживалась. Нужно аутентифицированное шифрование (AEAD) для заголовка, записей и вложений, работающее под Native AOT на всех целевых платформах.

## Решение

**AES-256-GCM** из `System.Security.Cryptography.AesGcm`:

- 96-битный случайный nonce на каждое шифрование, 128-битный тег;
- AAD связывает шифртекст с контекстом (`vaultId`, `itemId`, номер чанка) — файлы нельзя переставлять между хранилищами и записями;
- для вложений — потоковая конструкция STREAM поверх GCM (чанки 64 KiB).

Идентификатор шифра хранится в заголовке хранилища, поэтому его можно сменить новой версией формата.

## Альтернативы

- **XChaCha20-Poly1305** (через libsodium): 192-битный nonce безопаснее при случайной генерации и быстрее без AES-NI. Отказались, чтобы базовое шифрование не зависело от нативной библиотеки. Можно вернуться, если ADR 0002 будет принят и появится причина.
- **AES-CBC + HMAC**: корректно, но сложнее и без преимуществ перед GCM.

## Последствия

- Ограничение GCM: не более ~2³² шифрований одним ключом при случайных nonce. Для личного хранилища недостижимо; на всякий случай предусмотрена ротация производных ключей.
- `AesGcm` требует аппаратной поддержки на некоторых платформах — проверяется в CI (`AesGcm.IsSupported`).
